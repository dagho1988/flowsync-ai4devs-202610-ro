# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository

FlowSync: a TypeScript monorepo with two independent npm projects (no root `package.json`, no workspaces):

- `backend/` — AdonisJS 7 API (Lucid ORM on SQLite, VineJS validators, access-token auth).
- `frontend/` — React 19 + Vite 8 SPA. Currently still the Vite starter template; the intended UI kit is shadcn/ui (components are copied into the repo, not installed as a dependency).

The backend auth API is considered done: unless a task explicitly says otherwise, read it to learn the contract but don't modify it. Frontend work happens in `frontend/`.

`prompts.md` at the root is a course deliverable where the user logs prompts verbatim; don't rewrite or "clean up" its entries.

Requires Node.js 24+ (the backend runs `.ts` directly; older Node fails with `Unknown file extension ".ts"`).

## Commands

Backend (run from `backend/`):

```bash
npm install
cp .env.example .env && node ace generate:key   # first time only
node ace migration:run                          # creates tmp/db.sqlite3 and regenerates database/schema.ts
npm run dev                                     # http://localhost:3333, HMR
npm test                                        # node ace test (Japa)
node ace test --files tests/functional/foo.spec.ts   # single file
node ace test functional                        # single suite (unit | functional)
npm run lint && npm run typecheck
npm run format                                  # prettier (@adonisjs/prettier-config)
```

Frontend (run from `frontend/`, in a separate terminal from the backend):

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # tsc -b && vite build — also the typecheck
npm run lint     # oxlint
npm run format   # prettier --write src (format:check to verify)
```

The frontend has no test runner. Prettier (`.prettierrc.json`: no semicolons, single quotes) also runs automatically on every `frontend/src/**` file Claude edits, via the PostToolUse hook in `.claude/settings.json` → `.claude/hooks/format-frontend.mjs`.

## Backend architecture

Request flow: `start/routes.ts` → controller (`app/controllers`) → VineJS validator (`app/validators`) → Lucid model (`app/models`) → transformer (`app/transformers`) → `ctx.serialize(...)`.

Things that span multiple files and aren't obvious:

- **Controllers are referenced via a generated index**: routes use `controllers.NewAccount` etc. from `#generated/controllers` (`.adonisjs/server/controllers.ts`). The `.adonisjs/` directory is regenerated by hooks in `adonisrc.ts` (`indexEntities`, Tuyau `generateRegistry`) when the dev server/ace runs — don't hand-edit it.
- **Models extend generated schema classes**: `User` extends `UserSchema` from `database/schema.ts`, which is auto-generated from migrations by `node ace migration:run`. Schema changes go in a new migration in `database/migrations/`, never by editing `schema.ts` or the DB. Custom column mappings live in `database/schema_rules.ts`.
- **Response envelope**: `providers/api_provider.ts` adds `ctx.serialize()`, which wraps every payload under `data` (`{ data: { user, token } }`). Use `serialize.withoutWrapping` to opt out. Transformers pick exactly which fields are exposed (the User transformer returns `id, fullName, email, createdAt, updatedAt, initials`).
- **JSON everywhere**: `force_json_response_middleware` makes all responses (including errors) JSON. Validation failures return 422 with an `errors` array of `{ message, rule, field }`; bad login credentials come from `User.verifyCredentials` (`E_INVALID_CREDENTIALS`, 400).
- **Auth**: default guard is `api` (opaque access tokens stored in `auth_access_tokens`, values prefixed `oat_`), sent as `Authorization: Bearer <token>`. A `web` session guard is also configured but unused by routes. CORS allows any origin in dev.
- Path aliases (`#models/*`, `#validators/*`, etc.) are defined in `backend/package.json` `imports` and point to `.js` paths; import with those aliases.

### Auth API contract (`/api/v1`)

| Method | Path | Auth | Body / notes |
|---|---|---|---|
| POST | `auth/signup` | — | `fullName` (nullable), `email` (unique, ≤254), `password` (8–32), **`passwordConfirmation`** (must match). Returns `{ data: { user, token } }` |
| POST | `auth/login` | — | `email`, `password`. Returns `{ data: { user, token } }` |
| GET | `account/profile` | Bearer | Returns `{ data: user }` |
| POST | `account/logout` | Bearer | Deletes the current token |

Note the signup validator requires fields (`passwordConfirmation`, password length rules) that a product-level ticket may not mention — check `app/validators/user.ts` before building forms against it.

## Tests

Japa suites are declared in `adonisrc.ts`: `unit` → `tests/unit/**/*.spec.ts`, `functional` → `tests/functional/**/*.spec.ts`. No tests exist yet; `tests/bootstrap.ts` already registers the API client, session and auth (`loginAs`) plugins plus DB assertions. `.env.test` uses the in-memory session driver.

## Process rules

Follow these on every task that changes code:

1. **New branch before touching code.** Branch off `main` before the first edit (`git switch -c <type>/<short-description>`); never work directly on `main`.
2. **Close with `/commit` and a pull request.** When the work is done, stage it and commit via the `/commit` skill, push the branch, and open the PR with `gh pr create` against `main`.
3. **Then run the reviewer.** Run the `adversarial-reviewer` subagent on that PR.
4. **In the chat, only the PR URL.** The final message is just the pull request URL — no summary, no review findings.
